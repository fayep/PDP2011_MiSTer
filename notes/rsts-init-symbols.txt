# Known INIT.SYS (RSTS V9.6) routine/data addresses.
# Format: <addr-octal> <name> [; <description>]
# Load with: disasm.py -x <file> ... -symfile notes/rsts-init-symbols.txt
# Addresses are file-offset = address (valid only under 64KB -- see
# notes/rsts-init-disasm.md's methodology section).

021042 ERRDSP ; shared error/dispatch handler, referenced from two
              ; adjacent device-table slots found at physical 041212/041216
              ; via a live-traced block-copy; JMPs through a patchable
              ; vector cell at 001720 whose real target is set by the
              ; specific caller about to dispatch an error (not itself
              ; part of the always-taken path)

056012 DEVCHK ; per-drive-type detection / device-present flag update:
              ; masks RLCS's drive-type field, compares against two type
              ; codes, sets/clears flag bytes at 027626/027631 accordingly

057230 DEVCHK_CONT ; continuation after DEVCHK -- sets PS=034340 (priority
                    ; 7, interrupts masked), a fresh SP, calls @#014674,
                    ; then dispatches on a #000777-masked flags word
                    ; against several bit patterns (045000/071000/102000/
                    ; 051000) -- looks like a compiled-in device/feature
                    ; bitmask, worth revisiting for the "N devices
                    ; disabled" count specifically

120576 SZRATIO ; size/ratio computation: shift-based software divide
               ; (ASR/ROR pair) then MUL #1000 / CMP #020000 clamp;
               ; reached repeatedly during the device-table walk below

121600 DEVWALK ; device-table iteration loop: masks/shifts a device
               ; number into a byte offset, looks up a per-device handler
               ; pointer via 045762(r2), dispatches through it via
               ; JSR PC,123764

123226 DEVWALK_ENTRY ; entry into DEVWALK from elsewhere (masks r0's low
                      ; nibble, branches to 121600 if nonzero)

023256 KIRESET ; defensive utility: saves r0/r1/SR0, temporarily disables
               ; the MMU, resets ALL of Kernel I-space PAR0-7 to a clean
               ; identity map (PDR=077406 full-access default, PAR
               ; incrementing by 0200 = one page per register) with the
               ; standard 177600 I/O-page-passthrough value in the last
               ; slot, then restores r0/r1/SR0 exactly as they were --
               ; called as the first step of the PAGE5/6 map-and-copy
               ; primitives below, presumably to guarantee a known-good
               ; state outside the two pages being manipulated

025006 MAPCOPY_PARAM ; PARAMETERIZED page-5/6 map+copy primitive: after
                      ; calling KIRESET (023256, which preserves r0/r1),
                      ; sets KIPAR5=r0, KIPAR6=r1 (caller-supplied, NOT
                      ; constants -- the strongest lead so far toward a
                      ; real generalized overlay mechanism), enables the
                      ; MMU, then block-copies between the two mapped
                      ; windows (direction chosen by comparing r0/r1) via
                      ; 024766/025100, disables the MMU, returns. WHO
                      ; calls this and what they compute for r0/r1 is
                      ; the open thread -- likely where a segment/overlay
                      ; NUMBER gets turned into an actual PAR value.

025120 MAPCOPY_FIXED6 ; sibling of MAPCOPY_PARAM: same KIRESET preamble,
                       ; but KIPAR6 is a FIXED immediate (002200), only
                       ; page 5 (if any) is caller-supplied

025204 MAPCOPY_PICK6 ; sibling: KIRESET preamble, then picks KIPAR6
                      ; between two fixed values (002600 or 002400) based
                      ; on comparing a stack parameter against #020000,
                      ; and adjusts that same stack parameter by adding
                      ; 140000 or 160000 depending on which branch taken

025262 MAPCALL_1600_2000 ; the generic "save PAR5/PAR6/SR0, map FIXED
                         ; 001600/002000, call through a stack-passed
                         ; entry point, restore" wrapper -- structurally
                         ; identical to 020102 (see below) but a
                         ; different fixed bank pair. Confirmed (live
                         ; full-boot capture) NOT overlay-load-specific:
                         ; hit thousands of times throughout the WHOLE
                         ; boot, long after the 22 SYSGEN-phase overlay
                         ; loads finish -- a generic call-through
                         ; primitive used pervasively. Directly
                         ; implicated as the real proximate caller for
                         ; the "N devices disabled" boot message: hit in
                         ; a tight repeating loop right before that text
                         ; prints, r1 constant at 041020 (a runtime-
                         ; built, all-zero-on-disk scratch table --
                         ; plausibly the device-status/disabled-flags
                         ; table), r0 cycling through small per-call
                         ; codes (000110/000075/000100/000103/000104)
                         ; -- see notes/rsts-init-disasm.md's Open
                         ; Questions #1 for the full writeup. 025262's
                         ; OWN internals were never disassembled this
                         ; session (unlike 025006/025120/025204 above)
                         ; -- natural next step.

020102 MAPCALL_4000_4200 ; the FIRST-FOUND instance of this wrapper
                          ; pattern (live-confirmed via repeated single-
                          ; stepping -- this is the "character print
                          ; loop" call site): save PAR5/PAR6/SR0, map
                          ; FIXED 004000/004200, call through a stack-
                          ; passed entry point (JSR PC,@(SP)+), restore.
                          ; Part of a larger dispatcher based near 020076/
                          ; 020370 (guarded by "CMP (R5),#6 / BNE 020210"
                          ; -- this is case 6; other cases go elsewhere,
                          ; not yet mapped)

154266 MMUPROBE ; major find: full MMU-state save + hardware probe.
                ; Saves Supervisor-I PDR0-7 (172300-172316, resetting
                ; each to 077406 as it saves it), Kernel-I PAR0-7
                ; (172340-172356), User-I PAR0-7 (177640-177656), and
                ; Kernel-D PAR0-7 (172360-172376) into a fixed buffer at
                ; 143602-143676. Installs a TEMPORARY bus-error trap
                ; vector (address 4) before touching anything risky --
                ; classic "probe memory/hardware, catch the fault
                ; harmlessly" technique. Also temporarily clears SR3 bit
                ; 2 around the Kernel-D portion. Almost certainly RSTS's
                ; memory-size or device-presence detection, run once
                ; during INIT startup. VERY plausibly upstream of the
                ; "N devices disabled" count, though the exact connection
                ; is not yet traced.

154550 MMUPROBE_STUB1 ; minimal bus-error handler body #1 (CMP (SP)+,(SP)+)
                       ; installed at 154306 as vector PC, restored at 025176-ish
154534 MMUPROBE_STUB2 ; minimal bus-error handler body #2, installed at
                       ; 154436 for the riskier Kernel-D-space portion

051012 RLCS_PTR1 ; pointer-to-RLCS data cell (value 174400), used by
                  ; DEVCHK (056026: MOV 051012,R0) -- same convention as
                  ; the boot block's own "157016" cell
072474 RLCS_PTR2 ; second pointer-to-RLCS cell; referencing code not yet
                  ; identified this session
077330 RLCS_PTR3 ; third pointer-to-RLCS cell; referencing code not yet
                  ; identified this session

115216 BUFSHRINK_TABLE_WALK ; CONFIRMED LIVE (SIMH, this session, single
                  ; execute-breakpoint at 115264 -- see method note below):
                  ; loop 115222-115260 walks a table from #043042 to
                  ; #043242 (0o200 bytes), comparing R0/R1 (loaded at
                  ; 115162 from a caller-supplied (R5)+ pair, bounds-
                  ; checked against @#102176/@#102200 -- the SAME memory-
                  ; size-bound cells the [[rsts-v96-hang-kipar5-nonidentity]]
                  ; memory entry's shrink-decision writeup already
                  ; extensively traces) against each table entry; a match
                  ; falls through to 115270/115274.
115274 BUFSHRINK_MSG_CALL ; `JSR R5,@#004610` right after a table match --
                  ; the same inline-parameter idiom used throughout this
                  ; codebase. Strong candidate for the ACTUAL call that
                  ; produces "Cannot use extra 12K of buffers."/"Reduced
                  ; to 11K." (this whole 115216-115274 block's virtual
                  ; range is KIPAR4's page; confirmed via the METHOD note
                  ; below to be reached from this exact live boot).
004610 MSGDISP_ENTRY ; `MOV R0,-(SP)` / `MOV (R5)+,R0` / `JSR PC,@#004624`
                  ; -- reads an inline word via the JSR R5 idiom into R0
                  ; (almost certainly a message-number/code, not a raw
                  ; string address) then dispatches through the vector
                  ; cell at 004624. This is a GENERIC low, always-resident
                  ; (page0, <64K, no overlay ambiguity) message-print
                  ; entry point -- everything below 64K in this immediate
                  ; area decoded consistently with the static file, unlike
                  ; 115216-115274 above.
004624 MSGDISP_VECTOR ; patchable vector cell dispatched through by
                  ; MSGDISP_ENTRY -- same pattern as the already-known
                  ; 001720 vector ERRDSP jumps through. Not yet resolved
                  ; to its live target this session.

METHOD NOTE (this session): 115216-115274 sits in KIPAR4's virtual page
                  (100000-117777), which -- like page 1 and pages 5/6 --
                  is NOT reliably `file-offset == address` even under
                  64K: the static init.sys bytes at file offset 115264
                  are all-zero, but a live SIMH breakpoint at 115264
                  (single `break -e 115264`, no other breakpoints --
                  multiple simultaneous breakpoints on this exact boot
                  phase measurably perturb timing and change which
                  overlay/config path gets taken, confirmed the hard way
                  this session) shows real code there, with SR0=000044
                  (MMU DISABLED, flat physical addressing) at that exact
                  PC. Resolved the REAL backing content by directly
                  correlating a `set rl debug` (bare -- `SET RL
                  DEBUG=OPS;RWR`'s selective-flag syntax is NOT wired up
                  in this build's pdp11_rl.c despite matching a working
                  prior-session recipe; only the bare `SET RL DEBUG` form
                  works here) transaction log's destination-address+
                  length pairs against the target address, rather than
                  guessing via KIPAR-value arithmetic (which also failed:
                  KIPAR4=000456 at this same breakpoint, but
                  file-offset(KIPAR4*0o100 + page-relative-offset) is
                  ALSO all-zero in the static file -- physical memory
                  here is populated by an actual disk DMA that doesn't
                  correspond to any fixed file offset, exactly the
                  already-documented "overlay banks aren't loaded via
                  simple file-offset math" finding, just now confirmed to
                  also apply to ordinary low-memory code reuse, not only
                  the page5/6 overlay mechanism). The matching read:
                  16 sectors (4096 bytes) starting LBN 928 (RLDA 002710,
                  cyl 11 sect 8), landing at staging address 0o110000 --
                  byte offset 2740 into that transfer = disk LBN 938,
                  byte 180 -- verified byte-for-byte identical to the
                  live-captured instruction window. Extracted that exact
                  16-sector block and re-disassembled it with
                  `disasm.py -x <block> 0o110000 0o115264 -scan`, which
                  is what decoded the 115216-115274 sequence above
                  correctly (unlike the flat whole-file scan, which
                  mis-decodes this address as HALT padding).
